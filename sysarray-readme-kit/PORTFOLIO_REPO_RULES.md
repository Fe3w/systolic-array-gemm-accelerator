# Portfolio repo rules (reuse for every project)

Target reader order: recruiter (30 s) → team lead / hiring manager (3 min) →
interviewing engineer (15+ min). The README serves the first two; `docs/`
serves the third.

## The first screen (what shows before scrolling)

1. **Title that says what it is**, not just a name: "X: a Y that does Z".
2. **Badges**: CI status (only if green), main language/tools, license. 4–5 max.
3. **Two-line pitch in bold**, in plain words: what you built + the single best
   result + one number that shows you understand it (for example, "model
   predicted every measured cycle").
4. **One visual**: GIF, demo video thumbnail or one clear figure.
5. **"Built with" line**: the keywords a recruiter matches against the job post.

## The README body (~1,000–1,500 words, in this order)

| Section | Purpose | Rule |
| --- | --- | --- |
| At a glance | 4–6 row table: area / result / source | Plain-language result first, units second; every row cites its source file |
| How it works | One end-to-end figure + 3–4 sentences | Show the whole stack, not just one block |
| The main thing for your target role | For GPU / accelerator / compiler roles: architecture, performance and compiler before verification and PPA | Order sections by the job you want, not by build order |
| Performance | One chart + cause → effect → what's left → next step | Always say what limits it now |
| Verification | 4–5 bullets: method, not just "has tests" | Name the golden model, randomization, coverage, seeds, CI |
| Cost (PPA / latency / memory) | Small table | Honest status; details in docs |
| Key design decisions | 3–5 bullets: "X over Y because Z; cost W" | Never just IDs like "D-012" |
| Run it yourself | One demo command + a short table | Include time estimates |
| Limitations | 4–6 bullets | Near the end, never in the pitch |
| Repository map | Table + links to every doc | |

## Deep dives go in `docs/`

One page per topic (PERFORMANCE, VERIFICATION, PPA or COST, ARCHITECTURE,
DECISIONS). Each starts with a one-paragraph summary and a link back to the
README. Move content, don't delete it.

## Numbers

- Every number traces to a file produced by a committed script; cite it.
- Label predictions as predictions.
- State ranges honestly (0.78–0.82 on the named shapes, not "~0.8 everywhere").
- Lead with what passed; report what's open plainly in the detail section and
  Limitations.

## Figures

- Generated by a committed script from committed data, with a smoke test.
- Before/after charts beat single-state charts: they show you changed
  something and measured it.
- Check every figure by eye for overlapping labels before committing.

## Repo hygiene

- Commit as you go, with meaningful messages; never backdate fake history.
- CI green on `main`; lint clean.
- Tag a `v1.0` release when done; write release notes with the headline results.
- About box: one-line description with the best number, 10–17 topics.
- Social preview image (1280 × 640) with title and 3–4 headline numbers.
- Pin the repo; strongest project first.
- Add the demo video link near the top once it exists.

## Pre-publish checklist

- [ ] First screen passes the 30-second test (show it to someone outside the field)
- [ ] Every number cited; predictions labelled
- [ ] All links work (run a link checker)
- [ ] Figures readable, no overlapping text
- [ ] CI badge green
- [ ] About, topics, social preview, release, pin done
